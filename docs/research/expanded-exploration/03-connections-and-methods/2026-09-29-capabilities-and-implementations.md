# Capabilities beyond the original five experiences

[Concern index](README.md)

The original wiki, source explorer, reasoning timeline, neighborhood map and focused collection help the user read and locate material. The following five proposals add activities with different outputs: avoid an already understood failure, rehearse a capability, detect an answer change, compare a decision alternative and deliberately test an analogy. None prescribes a home screen, storage engine, automatic promotion or proactive interruption policy.

| Additional experience | Value and concrete output | Sources and relations required | Jev's bounded contribution | Falsifiable next experiment |
| --- | --- | --- | --- | --- |
| **Failure-aware starting checklist** | On demand before a task, show a short checklist of relevant earlier failed approaches, the conditions that caused failure and the correction that actually passed. Example: an importer task prompts “preserve string IDs; include 007 versus 7 fixture.” | Task intent, failed code/log spans, corrected diffs, outcome evidence, project boundaries and method/exception links. A failure is useful knowledge even when it produced no final wiki conclusion. | Judge whether the current task shares the earlier failure mechanism and preconditions; separately judge missing evidence. Code checks source revision, exact commands and test results. | Freeze 20 new tasks, including six same-word/different-mechanism distractors. Compare lexical lookup, generative suggestions and Jev selection with expert labels. Reject proposal if it adds more irrelevant checklist items or misses the relevant correction as often as the simple baseline. Measure user time and omitted essential checks, not only relevance scores. |
| **Method rehearsal bench** | Turn a reviewed method into a local bounded exercise: run its invariant fixture, inspect a deliberately failing variant and try an exception. Output is executable evidence plus a scoped capability record. | Distinct agent threads, actual source code/output, exact input/output invariants, tool/environment versions and source-linked exceptions. Public recipes and personal observed outcomes remain distinct. | Select supported recipe candidates, choose the applicable exception exercise and decide which claim the output supports. Code executes only explicitly selected fixtures and records real results. | On five methods derived from previously unseen histories, have a reviewer reproduce the result from retained source IDs. Include a case with passing lint but failed behavioral tests. Reject if the system declares capability from prose alone or cannot reproduce the claimed fixture. |
| **Answer-change inbox** | Given an actively investigated question, show “new evidence, same answer” separately from “answer changed” and “conflict unresolved.” Output is a compact evidence delta that the user can inspect; no scheduled alert is assumed. | A question, prior evidence set, new source revisions, accepted claims, scope/time qualifiers and dependencies. A new note or repeated article is not necessarily a changed answer. | Independently judge answer movement, contradiction and missing scope. Code deduplicates exact evidence and routes linked-but-unacquired references separately. | Freeze ten question snapshots and ten subsequently acquired updates, including duplicates, scope exceptions and genuine reversals. Compare a changed-file trigger with Jev and generative deltas. Reject if harmless updates repeatedly demand attention or true reversals disappear. Human adjudication and source-recovery success determine utility. |
| **Counterfactual decision workbench** | Clone a recorded decision's assumptions into a comparison table: what would change if a constraint or alternative changed? Distinguish observed consequences from predictions and unknowns. Output is a test plan or bounded scenario comparison. | Explicit adopted/reversed decisions, constraints, actual consequences, failed alternatives, source timestamps and dependency links. A later event alone cannot establish causality. | Judge which recorded consequences depend on the altered assumption, and select source evidence. A generative model may propose hypotheses, but their status stays speculative until tested. | Use five decisions with known ablation/reversal results and five decisions without observed alternatives. Hide the ablation result, request the next discriminating experiment, then reveal it. Reject if the workbench states unobserved alternative outcomes as recorded facts or fails to recover decisive existing evidence. |
| **Analogy laboratory** | Present a speculative bridge between interests with two source anchors, the shared structure, the limits and one cheap experiment. The user can accept, reject or test it. Output is an evaluated hypothesis, rather than an automatic graph edge. | Source observations, structural parallels, counterexamples, applicability limits and later experiment outcomes. Wordplay and trivial organization ideas remain distinguishable from useful transfers. | Judge structural support and practical value separately; select disconfirming evidence and an applicable proposed test. It cannot generate the missing hypothesis by itself or prove transfer from similarity. | Freeze twelve cross-interest pairs: four useful transfers, four attractive but misleading parallels, four low-value/word-only links. Compare a lexical list, generative candidates and Jev review with user usefulness ratings. Reject if false transfers are promoted, if status collapses into fact, or if no useful unrecorded link is discovered. |

The controlled experiments in [the companion report](2026-09-29-connection-experiments.md) are feasibility probes for these proposals. They are not these larger user studies. The answer-change and counterfactual experiences are not implemented in this wave; the method bench has actual bounded executions, and the analogy laboratory has selection/status experiments.

## Four additional public implementation inspections

These repositories were selected from the existing repository inventory, rather than rerunning the original catalogs. Each was absent from the initial collection's 18 distinct inspected projects. Exact commit IDs and captured-file SHA-256 digests are in the [manifest](experiments/sources/manifest.json). Inspection covered named functions and sections, not an exhaustive repository audit. Captured code was read; only the two extracted pure string helpers described below were executed. Full application stacks were not installed or tested.

**Stanley (`devagrawal09/stanley-code`, `85f39e71db0f615b8ce6161a6672a2bf955fa7fd`).** Its failure-triage workflow distinguishes recognized log windows, duplicate fingerprints, unjudged limits, semantic failure type, causal relation to a diff, missing evidence and failed follow-ups. A concrete bridge from changed behavior to failure is required; temporal proximity, generic exit codes and vocabulary overlap do not suffice. It performs at most one allowlisted follow-up probe selected from the missing-evidence result. A conflicting “unrelated” answer is parked when the stack touches a changed file; regex compile/environment signatures remain observations. This offers a concrete pattern for a failure-aware checklist: retain what was seen, what was omitted and what would settle the explanation separately. These are observed implementation behaviors, not evidence of live classification quality. [Pinned failure-triage implementation](https://github.com/devagrawal09/stanley-code/blob/85f39e71db0f615b8ce6161a6672a2bf955fa7fd/src/workflows/triage-failures.ts#L131).

Its task-checking prompt judges a hunk's contribution to a coherent implementation, including configuration, exports and test registration, while rejecting directory proximity as proof. This is relevant to connections across a coding thread, a changed file and a test: the meaningful relation may require a manifest of changes, rather than each fragment proving the task alone. This report does not claim the actual check-task runner was exercised. [Pinned task-checking implementation](https://github.com/devagrawal09/stanley-code/blob/85f39e71db0f615b8ce6161a6672a2bf955fa7fd/src/workflows/check-task.ts#L128).

**Jev research pipeline (`shimo4228/jev-research-pipeline`, `6dbac2bcf4221908cc16c934093cb1c52b4666ef`).** `question_movement` separates no addition, new evidence with the same answer and a changed answer/opened doubt; contradiction is independent. Its thresholds are implementation choices, not defaults justified for this project. This gives the answer-change inbox an operational question beyond “is this new?” [Pinned movement module](https://github.com/shimo4228/jev-research-pipeline/blob/6dbac2bcf4221908cc16c934093cb1c52b4666ef/src/jev_research_pipeline/jev/question_movement.py).

The model's Unit carries exact start/end, source ID and source hash and rechecks the matching source slice. Judgment identity includes function, subjects, pinned model, state hash and bundle hash; thresholds live separately in Decision. The stage cache considers a record valid only while every output remains in the partition, allowing deleted outputs to be recomputed. Together these illustrate reproducible source and judgment records without assuming its graph store is the right Knowledge Garden store. [Pinned Unit and Judgment definitions](https://github.com/shimo4228/jev-research-pipeline/blob/6dbac2bcf4221908cc16c934093cb1c52b4666ef/src/jev_research_pipeline/model/nodes.py#L230), [stage-cache implementation](https://github.com/shimo4228/jev-research-pipeline/blob/6dbac2bcf4221908cc16c934093cb1c52b4666ef/src/jev_research_pipeline/store/stage_cache.py).

Its source-support function bypasses inference when whitespace-normalized, case-folded claim text is a substring of the source. Claim is documented as a verbatim Unit accepted by claim detection. The extracted helper test shows why importing only the shortcut is hazardous: quotations, negations and hypotheticals all contain the claimed text. This does **not** demonstrate an end-to-end defect in the repository, because the test intentionally bypasses its Claim/Unit and claim-detection preconditions. A general wiki relationship checker cannot assume those preconditions merely because the helper accepts text. [Pinned support helper](https://github.com/shimo4228/jev-research-pipeline/blob/6dbac2bcf4221908cc16c934093cb1c52b4666ef/src/jev_research_pipeline/jev/source_support.py#L62), [Claim definition](https://github.com/shimo4228/jev-research-pipeline/blob/6dbac2bcf4221908cc16c934093cb1c52b4666ef/src/jev_research_pipeline/model/nodes.py#L295).

**Skillbox (`kitze/skillbox`, `cda64ad3310abe690c6d497352791da4cfeb9a0a`).** Resource reads enforce active readable skill/revision snapshots, parse canonical URIs, verify file bytes against size/digest and record read activity separately from loading or activation. Package audits preserve stored bytes rather than silently normalizing YAML. These are useful boundaries if a learned method eventually becomes a reusable package: inspected evidence, a draft recipe, a read package and an activated capability should have different records. The MCP tool description distinguishes uncertain semantic relevance on deterministic fallback (`noMatch=null`) from a semantic no-match result; this pass inspected that advertised contract, not the underlying recommendation module. [Pinned resource-read module](https://github.com/kitze/skillbox/blob/cda64ad3310abe690c6d497352791da4cfeb9a0a/src/server/skill-resources.ts), [canonical URI/integrity implementation](https://github.com/kitze/skillbox/blob/cda64ad3310abe690c6d497352791da4cfeb9a0a/src/skill-manifest.ts#L61), [recommendation tool contract](https://github.com/kitze/skillbox/blob/cda64ad3310abe690c6d497352791da4cfeb9a0a/src/server/mcp.ts#L197).

Its import exclusions and embedded-secret checks are explicitly heuristic. Absence of their regex matches does not certify that arbitrary private histories are safe to publish. No private histories or configurations are included in this concern's artifacts. [Pinned import-safety module](https://github.com/kitze/skillbox/blob/cda64ad3310abe690c6d497352791da4cfeb9a0a/src/skill-import-safety.ts).

**Discern (`doeixd/discern`, `95c67914b20619da88c5a60076ac5898dfae1311`).** A procedure has a typed input, description, deterministic eligibility function and Effect program. A registry first filters eligibility; no candidates yields `None`, one candidate is selected by elimination, multiple candidates invoke a probabilistic classification with both probability and margin thresholds. Uncertainty has its own handler/failure and routed recursion has a depth bound. The router selects a procedure and cannot generate missing parameters; all registry members share an input type. These distinctions are relevant to choosing an applicable learned method without pretending a method title supplies runnable inputs. Its defaults (probability 0.7, margin 0.15, depth 8) are not endorsed for this project. [Pinned procedure interface and registry implementation](https://github.com/doeixd/discern/blob/95c67914b20619da88c5a60076ac5898dfae1311/src/procedure.ts#L34).

## Model boundary and unresolved choices

Current TypeSafe documentation says Jev takes text/structured text state, and questions in one request are independent. It cannot produce an unseen connection description or inspect original images/video directly. Known source IDs, exact checks, candidate acquisition and execution belong in code; generative models can propose hypotheses or drafts, with source fidelity tested separately. Our API calls used the documented OpenRouter System One endpoint and explicit configured key, and preserved raw usage/cost/model metadata. [TypeSafe state](https://docs.typesafe.ai/concepts/state), [OpenRouter compatibility/API contract](https://openrouter.ai/docs/guides/community/typesafe-sdk).

The tests favor keeping source facts and interpretation status outside long generated prose, but they do not settle storage layout. Whether the user wants speculative links visible by default, how many checklist items are tolerable, whether a method can be activated directly, and whether answer changes should interrupt work all remain open. The five experiments above can evaluate those choices with concrete outputs instead of asking the user to adopt an architecture now.
