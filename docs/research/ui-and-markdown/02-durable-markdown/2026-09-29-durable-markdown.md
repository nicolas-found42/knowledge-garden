# Lasting knowledge in Markdown: representation and update experiments

Research date: 2026-09-29 America/New_York (execution also falls on 2026-09-30 UTC). This continues the [confirmed working brief](../../../../.scratch/ideas/current-specification.md), [initial collection](../../initial-brainstorm/README.md), [expanded synthesis](../../expanded-exploration/2026-09-29-synthesis.md), and [navigation/provenance study](../../expanded-exploration/04-navigation-and-provenance/2026-09-29-navigation-and-provenance.md). No format or architecture is accepted here.

A readable page is insufficient as the only durable record. Typed relationships, evidence selectors, revision dependencies, user annotations, ordered trails, saved query/filter intent, saved view selection/layout, and pending/accepted/rejected refresh proposals can all live in `.md`. Original bytes remain distinct assets. The executed laboratory establishes a bounded reconstruction and conflict-handling example; it does not establish production durability or seamless Obsidian interoperability.

## Documentation-backed expectations

Official Obsidian help was inspected at commit `9cf8c2913e56830e75c13f33ba198d7e70b6d9ef`; [manifest](experiments/primary-source-manifest.json) retains exact file hashes and access failures. Public help URLs returned authorization/robots errors in the web tool, so the first-party help Git repository supplied the documents. Repository documentation was read; repository code was not executed.

Obsidian supports both wikilinks and Markdown links, including percent-encoded paths, heading links and block references. The docs describe internal link updating for in-app renames and a configurable setting; they do not establish correctness for arbitrary external filesystem moves. Block IDs use letters, digits and dashes, and block references are an Obsidian extension. A stable metadata ID therefore needs separate app interpretation: it cannot silently turn an ordinary path link into an ID resolver. [Official internal links](https://github.com/obsidianmd/obsidian-help/blob/9cf8c2913e56830e75c13f33ba198d7e70b6d9ef/en/Linking%20notes%20and%20files/Internal%20links.md), [manage notes](https://github.com/obsidianmd/obsidian-help/blob/9cf8c2913e56830e75c13f33ba198d7e70b6d9ef/en/Files%20and%20folders/Manage%20notes.md).

Properties provide text, lists, numbers, booleans and dates. Quoted wikilinks can appear in properties; nested properties and Markdown formatting in properties lack ordinary property-editor support. Flat atomic metadata plus visible prose/link evidence is consequently a viable representation to test. JSON frontmatter is documented but can be rewritten as YAML, so byte-preserving editor assumptions require actual measurement. [Official properties](https://github.com/obsidianmd/obsidian-help/blob/9cf8c2913e56830e75c13f33ba198d7e70b6d9ef/en/Editing%20and%20formatting/Properties.md).

A `query` fenced block embeds Search results. Search can query properties, but its content coverage is notes/canvases; this does not promise OCR, PDF text, semantic retrieval or natural-language cited answers. The application can retain all four requested query experiences while storing their lasting intent/results in Markdown. Obsidian supplies independent reading/navigation and a subset of query UI. [Official Search](https://github.com/obsidianmd/obsidian-help/blob/9cf8c2913e56830e75c13f33ba198d7e70b6d9ef/en/Plugins/Search.md).

Obsidian documents native Markdown, images, audio, video and PDF, with media codec dependence. `.txt`, presentations and office documents are not in that native list. Keeping those original formats is compatible with the brief, but linking or opening an unsupported original requires a tested external-open behavior; embedding it cannot be assumed. Images, note blocks and PDF page selectors have documented embed syntax. [Accepted formats](https://github.com/obsidianmd/obsidian-help/blob/9cf8c2913e56830e75c13f33ba198d7e70b6d9ef/en/Files%20and%20folders/Accepted%20file%20formats.md), [embeds](https://github.com/obsidianmd/obsidian-help/blob/9cf8c2913e56830e75c13f33ba198d7e70b6d9ef/en/Linking%20notes%20and%20files/Embed%20files.md).

Standard links, headings and code blocks have CommonMark definitions. YAML properties, wikilinks, tables, dynamic query fences and block selectors are conventions/extensions beyond that core specification. “Markdown” alone does not specify a portable schema or renderer behavior. [CommonMark 0.31.2](https://spec.commonmark.org/0.31.2/).

## Three viable representations

The [executed comparison](experiments/representation-results.json) reconstructs the same authored, evidence-bearing relationship from [three actual Markdown files](experiments/representations/). All three recover eight fields exactly; measured parsing takes roughly 0.01–0.06 ms for this single tiny record. These values cannot rank production performance.

| Representation | Useful behavior | Cost or risk to test |
| --- | --- | --- |
| A: one relationship note, flat properties and prose | Relationship has its own ID, backlink target, status, review text and evidence links; ordinary property inspection is documented | More files; graph clutter; many-edge scale; redundant readable links and IDs must agree |
| B: relationship record fenced inside a page | Keeps page context; arbitrary structured fields stay in Markdown; evidence links appear in ordinary prose | Nested structured record is visible source/code, not native property UI; external editing and parser robustness; link text inside code is not equivalent to ordinary backlinks |
| C: Markdown table ledger | Compact comparison, batch editing and human scanning; explicit typed/evidence fields | Escaping, multiline evidence, row IDs and row-level anchors; large ledgers create coarse file backlinks and conflict boundaries |

None loses application capabilities by definition: a custom app can parse each and expose the full relationship/evidence interface. Ordinary Obsidian has different affordances for each. These are viable schema families, not a selected production design. The comparison uses deliberately minimal shape-specific parsers, not a general YAML/CommonMark implementation.

## Actual controlled disk results

[26 assertions](experiments/expected.json) were fixed before execution; [retained run](experiments/runs/20260929-204708.json) passes 26/26. The test copies the vault into a temporary directory, mutates the copy, and retains platform/Python version, fixture/assertion digests, each error/elapsed time and the final rebuilt index. Per-assertion elapsed time ranged from 0.0005 to 1.343 ms (median 0.603 ms); this is a tiny fixture, not a collection-scale benchmark. No API requests, token cost or inference latency applies.

- Pages, sources, relationship, annotation, trail, saved search and saved view reconstruct from Markdown. Writing a derived index, deleting it and rebuilding produces an identical index. This establishes reconstruction for the fixture's modeled fields; it does not demonstrate a semantic/vector index or thumbnail rebuild.
- An external page edit changes the authoritative file digest and appears on rebuild. A moved/renamed file resolves by persistent ID in the app's reconstructed registry. The old ordinary path link breaks; a controlled explicit repair preserves its evidence anchor. This is an observed filesystem/custom-parser behavior, not a claim that Obsidian rewrites external moves.
- A heading change invalidates the old heading selector in the fixture. A prose edit retains a block ID; deleting it makes the ID unresolved. Selector survival does not establish that the altered prose still supports a claim. Existing [provenance anchoring results](../../expanded-exploration/04-navigation-and-provenance/2026-09-29-navigation-and-provenance.md#anchor-experiment-recover-and-abstain-separately) similarly separate recovery from current support.
- Duplicate IDs create a conflict bucket and remove the ambiguous ID from the usable registry. The parser never silently chooses the last file. Unknown flat properties survive; duplicate property names fail closed. This parser only accepts its narrow JSON-compatible YAML subset; normal Obsidian multiline YAML lists are an untested parser gap.
- Two separate source IDs retain identical asset bytes/hashes. A separate Markdown revision record keeps the same source identity, an independent record ID and revision `r2`, and a different byte hash; the historical relationship retains its `r1` evidence dependency instead of silently adopting the newest bytes. A byte-dedup store can consequently share a blob without merging acquisition identity. The fixture records a two-revision supersedes pointer but does not implement dedup storage, revision branching or an acquisition workflow: those remain alternatives to investigate. Missing and corrupt originals are flagged while their Markdown source records remain available.
- Refresh creates a reviewable `.md` proposal with target/source IDs, both base hashes, a visible unified diff and full replacement text. It does not mutate the page before acceptance. An intervening page edit blocks acceptance without losing it; an intervening source edit blocks acceptance too. Fresh acceptance preserves the user notes and external appended sentence because those bytes are retained in the proposed replacement. Rejection remains a Markdown state record.

The hash guards demonstrate **sequential** stale-proposal protection. The final check and write are separate filesystem operations: the experiment does not close a simultaneous writer race. A production mechanism needs an atomic write protocol, app serialization and recheck strategy, plus explicit policy for external tools that do not share locks. Hash-based rejection is a useful conservative option; automatic three-way merging, section ownership and per-claim updates remain untested competing options. Accepted/rejected state records also need tamper/conflict semantics. These are research gaps, not approved architecture decisions.

## Actual macOS watcher experiment

A separate [Node `fs.watch` experiment](experiments/watch_macos.mjs) ran on local macOS with Node `v26.9.0`. Before interpreting results, current first-party Node v26.10.0 documentation was read: callbacks carry `rename`/`change`; macOS directory watching uses FSEvents; filenames are not guaranteed; file watches follow an inode and may stop reporting replacement-file changes. Platform and environment caveats mean a watcher is a notification source rather than a durable event ledger. [Official Node filesystem documentation](https://nodejs.org/api/fs.html#fswatchfilename-options-listener).

The [seven frozen assertions](experiments/watcher-expected.json) cover an append, editor-style atomic save by renaming over the file, post-save append, external rename, burst creation of 40 notes, removal and a full hash rescan. Two bounded runs and full event timestamps are retained. The [first run](experiments/runs/watch-2026-09-30T00-49-07.893Z.json) passed 7/7 with 51 callbacks. Its expected append hashes were read back after mutation; a stronger second run derives those expected hashes from pre-mutation bytes and intended edit strings. The [second run](experiments/runs/watch-2026-09-30T00-49-28.761Z.json) also passed 7/7 with **56 callbacks and 55 final files**, including five initial callbacks despite watcher creation following fixture copy. No watcher errors occurred.

Both runs produced three directory notifications for the two-step atomic save, two for an external rename, and 41 during a 40-note burst. The single-file watcher saw the first append and replacement, then **no callback for the post-replacement append**; the directory watcher saw that edit. This is actual observed behavior consistent with the documented inode caveat. Event count/order cannot be interpreted as one durable edit record per notification. The retained phases classify callback delivery time and can include delayed notifications from earlier operations.

An 80-ms debounced directory notification schedules a content rescan. The independent final rescan exactly matches the intended path-to-byte-hash map, resolves the renamed observer's stable ID, includes every burst note, removes the deleted annotation and retains replacement/post-replacement content. Controlled adapter-level thinning then discards every second captured event; another full rescan still recovers the same final state. This simulated thinning demonstrates that reconciliation does not need a complete operation log; it is **not** evidence that macOS lost those notifications. The observed notification variation and surplus callbacks demonstrate why event-count assumptions are unsafe; actual OS coalescence was not isolated or proven.

The fixture and all mutations lived in an OS temporary copy, cleaned after capture. Earlier results remain intact. There were zero provider calls. This bounded local experiment does not measure large-vault scan cost, sleep/wake, root replacement, sync/cloud/network filesystems, overflow, concurrent ingestion, or production reliability. It also does not verify Obsidian external-edit behavior.

## Plugin-free vault and actual interoperability gap

The [disposable vault](experiments/disposable-vault/START%20HERE.md) contains ordinary links, explicit block selectors, properties, image embeds, a Search query fence and mixed durable records. Original text and image assets remain distinct from knowledge notes. The PNG is a controlled one-pixel image; this is an interoperability syntax fixture, not a realistic photo or a media-quality test. An original `.txt` link intentionally surfaces the native-format boundary.

**No actual Obsidian UI check was executed.** The root researcher found no installed Obsidian app in `/Applications`, `~/Applications`, or a bundle-ID metadata search. No application was installed and no global app configuration was changed. The [live checklist](experiments/README.md#live-checks-to-retain-separately) preserves actual viewing, backlinks, property behavior, embeds, external edit observation, in-app rename, external move and anchor checks as required future validation. Documentation-backed expectations and 26 successful disk invariants do not satisfy that missing validation.

## Questions for the later specification

Compare page-local records versus relationship notes versus ledgers at realistic density; define duplicate-ID remediation without arbitrary merges; choose whether original-byte dedup is physical only; define durable source-revision and missing-original history; test refresh proposals with real external-editor concurrency; decide how visible links and ID references reconcile after moves; and complete actual Obsidian checks on the varied photo/PDF/video/presentation corpus. All eight visualizer purposes and all four query modes remain within scope: storage research here neither removes them nor promises their Obsidian UI equivalents.
