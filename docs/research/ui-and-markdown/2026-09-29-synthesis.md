# What the interface and Markdown experiments establish

[Collection](README.md) · [Evidence map](requirement-evidence-map.md) · [Next interview brief](decision-brief.md)

The strongest direction is a collection whose durable knowledge remains readable Markdown, with several views over the same item/evidence identities and explicit handling of uncertainty, missing sources and externally changed files. This is a research recommendation, **not an accepted architecture**. All firm requirements in the [confirmed brief](../../../.scratch/ideas/current-specification.md) remain in scope. No default home, schema, inference policy or Mac stack was selected.

This collection extends both prior studies: their source-context/candidate-coverage failures remain relevant, while this wave adds general personal-file examples, three substantially different interaction compositions, file-state experiments, semantic search/cited-answer checks and measured rendering. The [initial study](../initial-brainstorm/README.md) and [expanded study](../expanded-exploration/README.md) remain intact, including their original failures and usage ledgers.

## Findings with practical consequences

**A Markdown contract can cover richer state than prose, but needs an explicit schema.** The durable laboratory reconstructs pages, typed links, annotations, source revisions, ordered trails, saved searches/views and proposal state after discarding a derived index. All three tested representation families preserve an eight-field evidence-bearing relation: a separate relation note with flat properties, a record fenced within a page, and a table ledger. This proves a small round trip, not a mature parser or large-vault workflow. Flat readable metadata aids ordinary navigation; more relation files can add clutter; compact ledgers make conflicts/anchors coarser. [Durable findings](02-durable-markdown/2026-09-29-durable-markdown.md).

**Stable identity and ordinary links solve different problems.** An externally moved note still resolves through its ID in the app's rebuilt registry, while the original Markdown path link breaks. A repair restores that link in the fixture. Ordinary Obsidian cannot be assumed to understand a custom identity field. Unknown/duplicate IDs and missing/corrupt original assets need visible recovery states. Byte-identical sources can share physical storage without becoming the same acquisition. Retaining the original revision keeps old evidence inspectable after a new version arrives. [Identity and anchor experiments](02-durable-markdown/2026-09-29-durable-markdown.md).

**External editing requires state reconciliation and guarded writes.** The actual Mac watcher produced 56 callbacks across a 55-file final fixture. Watching one file missed the later append after an atomic replacement; watching the directory and rescanning recovered the intended bytes. Notifications are useful triggers, not complete durable histories. Separate Markdown proposals with page/source base hashes rejected stale acceptance and preserved external text. The experiment's final hash check and write are sequential: a simultaneous writer race remains untested. No automatic merge policy is accepted. [Watcher and proposal records](02-durable-markdown/experiments/README.md).

**One evidence set can support quiet reading, research and a canvas.** The three [clickable concepts](03-interface-concepts/README.md) preserve selection, filters, comparison and in-memory trail while changing composition. Reading has a narrow page and on-demand evidence; the workspace keeps related evidence beside it; the canvas begins at a wide collection map with context below. All eight requested purposes have an inspectable route. These are working research controls over 27 public/controlled items, not a production Markdown renderer/importer. Meaning search/answer UI demonstrations are explicitly labeled; actual model tests are separate. The fixed prototype selector, persistent purpose controls and page toolbar still consume substantial space in the quiet view. The later interview should use the examples to decide what disappears during reading, rather than infer a preferred default from this implementation.

**Rendering a large collection and making it understandable are separate questions.** Actual browser runs draw up to 50,000 nodes and 400,000 synthetic directed edges, retaining every generated edge. At that largest density, median drawing submission is 9.4 ms, but next-frame elapsed time ranges 18.6–59.4 ms. A 12-group summary submits in approximately 0.1 ms, excluding its approximately 0.6 ms aggregation. The point-only test builds a spatial index for 50,000 points in median 3.3 ms and performs 100 bounded hit tests in 0.2 ms. These are deterministic Canvas fixtures without force simulation, media cards, meaningful clusters, full keyboard/screen-reader item access or real graph-navigation tasks. Neither the 0.1 ms group figure nor the 9.4 ms submission figure establishes frame rate or human usefulness. [Actual full records and interpretation](03-interface-concepts/browser-results.md).

**Semantic retrieval improves this fixture, while showing why failure type matters.** On 16 frozen development requests, lexical first-result/abstention correctness is 8/16; broad Jev and top-five reranking each score 14/16. Broad selection finds all 12 answerable targets but returns two gap records where the strict metric expects abstention. Reranking handles those unavailable-evidence queries, but cannot recover the two omitted answerable targets. A gap record may still be valuable in an exploratory interface when plainly labeled unavailable; selection is not itself a factual answer. Three code-owned relational queries return their exact expected sets. [Search report](04-search-and-timelines/2026-09-29-search-and-timelines.md).

**Citations still need origin and context, not just valid targets.** Six independent answers produce 13 sentences with valid IDs; four quote strings fail exact matching. Of the sentences, an independent researcher audit finds 11 context-supported, one qualified and one unsupported. The unsupported sentence promotes a deliberately controlled caption into a statement about a real photo's date, despite quoting it exactly. Jev accepts all 13. This is a useful successor to the earlier wiki qualification-loss result and a concrete item to inspect in the next interview. [Sentence-by-sentence audit](04-search-and-timelines/answer-audit.md).

**The three timeline meanings need distinct stored dates.** Activity time, explicit reasoning events and dates described by sources remain separate. A 2026 import does not move a 2024 event; a May-only date overlaps May 17; an unknown timestamp stays outside ascending/descending chronology. Nine controlled assertions and a browser check of the events/descending controls support those specific behaviors. Acquisition replay does not yet reconstruct relationship changes. Natural cross-thread chronology, date extraction and uncertain time presentation remain open. [Timeline evidence](04-search-and-timelines/2026-09-29-search-and-timelines.md#three-time-axes).

## What to borrow from precedents

The [13-app primary-source survey](01-precedents-and-stacks/2026-09-29-precedents-and-stacks.md) identifies behaviors to compare, rather than a winner. Photos/Eagle suggest remembered person/place/date/format clues and previews for ordinary data; Zotero/LiquidText/Heptabase suggest source-linked excerpts and context recovery; DEVONthink suggests quiet related-item suggestions; Curio/Scrintal/Tinderbox/TheBrain suggest changing arrangement without losing connected material; Readwise suggests keyboard-centered reading; Kagi Quick Answer demonstrates an answer action attached to search without needing conversational follow-ups. These are documented precedents, not measured app usability.

Two Obsidian mechanisms cannot simply become the product contract: core Canvas stores `.canvas` JSON, and its graph time-lapse uses file creation time. Durable view state here must instead have a Markdown representation, and timeline semantics must remain explicit. The app can provide all requested capabilities while Obsidian supplies independent file viewing/navigation; feature parity of interfaces is not required. [Primary-source details](01-precedents-and-stacks/2026-09-29-precedents-and-stacks.md).

SwiftUI/WKWebView, Tauri 2 and Electron all remain plausible. Their documented file/open/watch/rendering primitives support integration paths for every firm requirement. None has yet been packaged or compared for real memory, native focus, file bookmarks, media rendering or signing. The simple web research prototype is not evidence that Electron or any web-first stack has been chosen. [Per-requirement stack comparison](01-precedents-and-stacks/2026-09-29-precedents-and-stacks.md#three-viable-mac-stack-families-without-selecting-one).

## Evidence that is still missing

Actual Obsidian interoperability is the most important unavailable check. Obsidian was absent from both standard application directories, Spotlight bundle-ID results and the live application inventory. A disposable vault, pinned official documentation and exact check procedure exist; no installed app was exercised. Seamless links/backlinks/properties/media/external-edit/rename behavior remains unverified. This requirement was not weakened.

No human usability study, preferred default layout, complete accessibility conformance, semantic clustering quality, face recognition, generalized file extraction, local vector model, production answer reliability, concurrent external-write safety, native app package or integrated 50k-item navigation has been established. The matrix assigns each gap to an explicit decision or validation task. Controlled demonstrations should help the next interview define acceptance criteria without claiming these gaps are solved.

## Scope, privacy and accounting

The UI uses 27 public/controlled items and 21 assets. Nine real personal files were separately copied/structurally checked in restricted local storage; original hashes were unchanged. No private filenames, raw text, precise mappings or copied private assets enter this repository. No conversation URL destination was fetched. Public documentation was independently selected. Historical research records remain preserved.

The new [provider ledger](usage.json) totals 44 successful measured calls, 80,977 input tokens, 5,804 output tokens and **$0.005773986 reported router cost**. This excludes previous waves, coding agents, browser chooser/helper calls and unreported costs. Results retain actual request/response bodies, source/fixture hashes, model IDs, timings, semantic failures, failed source acquisitions and a browser download timeout. The subsequent local capture endpoint retained complete benchmark outputs without requiring a successful browser download.
