# Retrieval repositories: executable semantic views, source freshness, and context recovery

Research date: 2026-09-29. This fourth research assignment inspected **10 repositories at pinned commits** and made **105 explicit SDK requests** across four experiments plus service retries and composition follow-ups. These are development probes over small synthetic fixtures, not general benchmarks or a production design. The broad repository inventory is in the [landscape](../03-retrieval-and-navigation/2026-09-29-repository-landscape.md); these findings go deeper into different retrieval and context mechanisms.

## Evidence and method

Archives were retrieved by immutable GitHub commit SHA and statically read as data. No repository install scripts, services, benchmarks, or upstream tests were executed. The [source manifest](experiments/retrieval-repos/source-manifest.json) records all 10 commits, inspected paths, file hashes, line counts, and immutable primary-source URLs. Test assertions described below were **read**, not independently run. No claim here establishes package production readiness.

The live TypeSafe [documentation index](https://docs.typesafe.ai/llms.txt), [Python SDK](https://docs.typesafe.ai/sdk/python.md), [Choice](https://docs.typesafe.ai/primitives/choice.md), [Noul](https://docs.typesafe.ai/primitives/noul.md), [state](https://docs.typesafe.ai/concepts/state.md), and [function-calling cookbook](https://docs.typesafe.ai/cookbooks/function_calling.md) were read. Markdown pages failed through the web reader but returned HTTP 200 through direct HTTPS. The integration uses SDK 0.7.2, explicit existing `OPENROUTER_API_KEY`, base URL `https://openrouter.ai/api`, and `typesafe/jev-1.13`. Only synthetic strings were submitted. Independent questions share state; branch answers cannot consume answers from the same request.

## Repository mechanisms worth transferring

### JevSQL: semantic decisions as refreshable data

[Workflow code](https://github.com/EugeneBoondock/jevsql/blob/45f3862f679c064e371a800c2fcc0c5b8b90c6c6/src/workflows.mjs) materializes a SELECT into an ordinary keyed SQLite table, saves the SQL, parameters, model and cache namespace, logs added/updated/removed rows, and rolls back a failed refresh through a savepoint. [Workflow tests](https://github.com/EugeneBoondock/jevsql/blob/45f3862f679c064e371a800c2fcc0c5b8b90c6c6/test/workflows.test.mjs) asserts zero new requests on an unchanged refresh, only changed-input judgments after edits, persistence across restart, and rollback without damaged history. This is a concrete pattern for a rebuildable Markdown-derived semantic view: “notes establishing current storage decisions,” “constraints applicable to a task,” or “sources supporting this statement.” The output can be inspected with ordinary queries.

[Judgment identity](https://github.com/EugeneBoondock/jevsql/blob/45f3862f679c064e371a800c2fcc0c5b8b90c6c6/src/functions.mjs) hashes model, question kind, question wording, criteria, state and namespace. [Packing code](https://github.com/EugeneBoondock/jevsql/blob/45f3862f679c064e371a800c2fcc0c5b8b90c6c6/src/planner.mjs) deduplicates shared row state and packs multiple question/row pairs into bounded requests; its token estimate is approximate. [Exact-span decisions](https://github.com/EugeneBoondock/jevsql/blob/45f3862f679c064e371a800c2fcc0c5b8b90c6c6/src/decisions.mjs) validates candidate spans actually occur in the source before a Choice selects one. The opportunity is reusable semantic columns and change receipts, rather than new natural-language SQL generation. A matching cache key establishes identical judgment input, not that the canonical source is still current; the source adapter must refresh source identity/revision first.

### s1s: a semantic evidence interface with attributable losses

[Question surface](https://github.com/cpaczek/s1s/blob/8c433affb3086a91bca2a4d384505eeeb98feed7/src/questions.ts) centralizes question builders and rubrics: distinguish direct implementation from incidental use; judge candidate membership, general-purpose plumbing, runtime role, explanatory blocks, and real reference edges. Code constructs the flow from actual files and extracted references; selected comments supply summaries. [Search composition](https://github.com/cpaczek/s1s/blob/8c433affb3086a91bca2a4d384505eeeb98feed7/src/nav/search.ts) separates map/find/walk and preserves partial/absent verdicts. [Loss attribution](https://github.com/cpaczek/s1s/blob/8c433affb3086a91bca2a4d384505eeeb98feed7/src/nav/attribution.ts) locates losses at unseen/unretrieved, first hop, descent, shortlist, verify, or rank. This is a useful diagnostic schema for wiki search failures: observe the stage that lost the evidence, then adjust the stage instead of treating every miss as reranking failure.

[Explicit limitations](https://github.com/cpaczek/s1s/blob/8c433affb3086a91bca2a4d384505eeeb98feed7/docs/limitations.md) explicitly warns that extracted references are incomplete, a flow is not a runtime trace, a found threshold does not mean complete, and even full file examination does not establish semantic completeness. [Provenance tests](https://github.com/cpaczek/s1s/blob/8c433affb3086a91bca2a4d384505eeeb98feed7/test/retrieval-provenance.test.ts) inspects source/corpus parity in benchmark reuse. None of its cookbook-derived thresholds or benchmark headlines are transplanted here. The transferable feature is a reading guide made from observed links and source spans, accompanied by coverage gaps.

### Jev-Mem: typed graph needs and explicit traversal budgets

[Typed query questions](https://github.com/libingzheren/Jev-Mem/blob/7ab0c73c6d8f4f611ad252c1e6ba8083f8df0e44/memory/jev_questions.py) asks independent routing Nouls for semantic, temporal, causal, entity, multi-hop and recency needs. Traversal separates relevance, relation usefulness, new information and corroboration; stopping separates sufficient evidence, useful continuation, missing evidence and unresolved contradiction. [Traversal controller](https://github.com/libingzheren/Jev-Mem/blob/7ab0c73c6d8f4f611ad252c1e6ba8083f8df0e44/memory/jev_mem_retrieval.py) binds these judgments to vector/keyword anchors, active graph neighbors, per-graph allocations, calls, deadline, depth, node and edge caps. It ranks transitions from configured weights, so a useful dimension can compensate for a weak one; that policy needs targeted testing where missing required evidence must block an answer.

[Budgeted client](https://github.com/libingzheren/Jev-Mem/blob/7ab0c73c6d8f4f611ad252c1e6ba8083f8df0e44/memory/jev_client.py) retains distinct Noul/Choice structures, hashes complete request state including backend, serializes local-backend retrieval slots, and exposes budget/fallback events. This suggests exposing a query's evidence needs and actual budget use to a coding agent. It does not remove embedding dependencies or prove graph traversal is superior to a simpler candidate pool.

### TierMem: acquiring raw evidence when summaries cannot answer

[Sufficiency questions](https://github.com/FreedomIntelligence/Tiermem/blob/dba57bf2ce91a9920fdebaf5ffb0e6fc029fc398/jev_tiermem/providers.py) asks whether evidence supports a complete answer with names, dates, values and relationships, rejecting topic overlap alone. [Tiered retrieval code](https://github.com/FreedomIntelligence/Tiermem/blob/dba57bf2ce91a9920fdebaf5ffb0e6fc029fc398/jev_tiermem/system.py) first judges summaries, then loads their linked raw IDs plus local raw search candidates; bounded rounds record added IDs, evidence size and stop reason. Optional deeper search uses another model to propose keyword queries. Retrieved evidence can be returned to a host through [MCP evidence interface](https://github.com/FreedomIntelligence/Tiermem/blob/dba57bf2ce91a9920fdebaf5ffb0e6fc029fc398/jev_tiermem/mcp_server.py) rather than requiring its own answer generator.

[Raw recovery tests](https://github.com/FreedomIntelligence/Tiermem/blob/dba57bf2ce91a9920fdebaf5ffb0e6fc029fc398/jev_tiermem/tests/test_agent_loop.py) contains a scripted test that evicts the working window, preserves raw history, and recovers a detail in a fresh loop. Citation promotion checks raw IDs and exact substrings in code before semantic support/utility/novelty gates. This supplies a recovery architecture for lossy wiki summaries, though a summary that confidently asserts a simplified fact can appear sufficient without revealing its omitted qualifier. The adapter must preserve source links and mark derivation or revision information.

### Winnow: reversible hiding and question-set ablations

[Question variants](https://github.com/GhalebDweikat/winnow/blob/51d80b945c74c8384bc47fa817179f668289afd8/sidecar/src/winnow/questions.py) implements default, structured and strict needed-block questions, plus a whole-output error question. [Retention policy](https://github.com/GhalebDweikat/winnow/blob/51d80b945c74c8384bc47fa817179f668289afd8/sidecar/src/winnow/policy.py) retains unjudged and uncertain blocks; a detected error retains the whole output, and tiny savings do not justify rewriting. [Recall interface](https://github.com/GhalebDweikat/winnow/blob/51d80b945c74c8384bc47fa817179f668289afd8/sidecar/src/winnow/mcp_server.py) exposes full cached text through source-key and line-range recall. The useful idea is hiding with a recovery handle rather than irreversibly deleting evidence. Its README advertises shadow mode and replayable judgments; those measurements were not reproduced here.

The strict phrasing explicitly rejects unrequested background. That can save context but is a poor fit for protocol rules, source limitations and negative user constraints. Treating all errors as always useful also retains obsolete errors after a verified fix. Our retention probe directly contrasts topical relevance with task correctness.

### Hermes compaction: protect actions and carry the whole-session goal

[Hermes adapter](https://github.com/picaye/jev-compaction/blob/ef5372d343eff22c1d5816d17d2742b16278dda3/hermes-compact.mjs) maps Hermes records into tool call/result pairs, maps judgments back through stable tool IDs, and retries long histories as smaller windows. It protects state-changing tool calls in code because previous model judgments dropped their record. It supplies a whole-session goal to each window; its comments describe near-uniform deletion when local windows lacked the original task. This is stronger evidence for deterministic action receipts and persistent task constraints than for asking semantic salience to own every deletion.

The adapter uses the first user message plus a later assistant outcome to construct a bounded goal. A changed task or an assistant's incorrect completion claim could mislead that state. This is a source-design hypothesis, not a reproduced bug. Exact original source history must remain recoverable.

### Pi compaction: call relevance differs from verbatim result relevance

[Two-question compaction](https://github.com/joelhooks/pi-fast-jev-compaction/blob/eb83f533f4fd10a08728b02c062c249afda5a4dc/src/core/decide.ts) asks two Nouls per unpinned call: whether knowing the call/input still matters, and whether its full output must stay verbatim. Code resolves keep, drop result, or drop call and pins recent/first records. [State fitting](https://github.com/joelhooks/pi-fast-jev-compaction/blob/eb83f533f4fd10a08728b02c062c249afda5a4dc/src/core/state.ts) pairs calls and results, extracts recent user goals, and fits bounded state; full result bodies are replaced by short omitted-result notes before judgment. [Pairing tests](https://github.com/joelhooks/pi-fast-jev-compaction/blob/eb83f533f4fd10a08728b02c062c249afda5a4dc/tests/core.test.ts) asserts pairing/pinning and omission of result bodies. Thus the model can decide from task and operation metadata while missing a unique qualifier inside a long result. Our raw-source probe targets that information loss, not a full upstream reproduction.

### Jevsearch: candidate relevance and answerability are separate

[Search server](https://github.com/kylemclaren/jevsearch/blob/1df37decb960b3c4826c71b41d3393c15a8f28d3/src/lib/jev-search-server.ts) batches one per-page Noul, a competing best-page Choice, and an answerability Noul; candidate excerpts are bounded. Its in-memory cache key is model plus normalized query within a handler instance constructed over a document set. This is adequate only while that instance's corpus/configuration remain fixed; hot-reloading a mutable corpus would need handler recreation or a revision-bearing key. We did not demonstrate a live stale-cache defect. Relevance/answerability are useful output fields, but neither certifies the source statement's current truth.

### Jev Retrieval: code and prose require different predicates

[Window questions](https://github.com/romeromarcelo/jev-retrieval/blob/d6af3725276b1dae65b43272b9df5357b5b6c017/src/jev/questions.rs) gives code windows subsystem-membership questions and document windows concept-coverage questions, then a listwise Choice among kept files. [Request cache](https://github.com/romeromarcelo/jev-retrieval/blob/d6af3725276b1dae65b43272b9df5357b5b6c017/src/jev/client.rs) hashes serialized request bodies for response caching. Changed sent evidence changes the key; a change outside an excerpt may not. Its comment saying entries cannot go stale is therefore about identical submitted bodies, not freshness of all canonical source content or provider behavior. Distinct code/prose predicates transfer well to mixed coding-chat notes and reference documents.

### Neo4jev: structured stages without generated graph queries

[Navigator code](https://github.com/jexp/neo4jev/blob/d157bbe496eb91813475156942bef1c6badfb342/src/neo4jev/navigator.py) chooses among real outgoing edges and asks whether the current node meets the goal, with topology, stage, call/depth/beam constraints. It supports explicit ordered stages as well as heuristic stage decomposition and trims long properties. A wiki adapter could use code-defined stages such as decision → rationale → verification and retain observed link provenance. Existing retrieval experiments already explore beam traversal and stopping, so this pass does not repeat that experiment or assume a graph database is needed.

## Four experiments and what they actually establish

All fixtures were written before requests. [Initial raw records](experiments/retrieval-repos/results-initial/raw.jsonl) preserve requests, state, criteria, answers, probabilities, usage, latency, labels and errors. [Follow-up raw records](experiments/retrieval-repos/results-followup/raw.jsonl) preserve retries and revised composition separately. A Noul cutoff of 0.5 is used only to count these development checks; it is not a deployment policy.

| Experiment | Observation | Interpretation |
|---|---|---|
| Current source versus cached statement, 20 requests | Revision-aware: 10/10 labels. Cached-only: 10/10 unknown. | Cached-only agreement with hidden current truth is 2/10, **not model accuracy**. All ten abstentions are correct because freshness evidence was withheld. A source hash change is code's signal to load a revision; Jev then judges whether the claim survives the change. |
| Topic-only versus correctness-aware retention, 20 requests plus one service retry | Topic-only 8/10 after recovery; correctness-aware 10/10. | Topic-only drops a protocol requirement and keeps an obsolete fixed error. Source identity, negative constraints and task dependency cases are included, but this easy sample does not establish general recall or calibration. |
| Typed query operators and binding, 38 successful initial checks plus two retry checks and follow-up | All initial typed operator/argument pairs: 17/20 checks. Branch-specific follow-up: 9/10 whole plans; 15/16 scored branch checks. | One generic argument question picks a follow destination rather than start and narrows a select into one source. Branch-specific speculative bindings plus code-owned select/all fix those. A remaining lookup instead of select returns only one source: syntactically valid but semantically incomplete. |
| Synopsis → raw-source acquisition, 20 initial requests, three service retries, ten dependent fetches | Final adaptive raw answer 9/10; action 8/10; 17/20 checks. All ten synopsis actions fetch, including one unnecessary fetch. | Fetching restores scope, adoption, timing and condition evidence. Some synopsis answers disagree with hidden raw truth because information was deliberately removed; these are withholding effects. One confidently stale synopsis is taken literally on the answer branch while the independently asked action still fetches. Code must consume the action before asserting a fact. |

The 80 initial requests produced 75 successful records and five `TypeSafeInternalServerError` records. Exactly those five frozen failures were retried separately and succeeded. Ten branch-specific plan requests and ten actual dependent raw fetch requests make **105 explicit requests, 100 successful responses**. The SDK may perform internal retries, so this is not an HTTP-attempt count. Recorded successful wire-response costs total **$0.002213148**, with **$0.001558494** from the first run and **$0.000654654** from follow-ups. Costs of failed/unobserved attempts are unknown; the recorded sum is not a complete invoice. Initial median successful latency was about **0.332 seconds** and total initial wall time about **43.83 seconds**, including errors/retries.

The acquired Markdown-authority source states “canonical notes are Markdown; SQLite is rebuildable,” yet the answer repeatedly chose unknown. This is a genuine conservative model miss on supplied evidence. The conditional-deployment source gives a clear current-local statement and receives no, but action chooses abstain: independent question inconsistency, not missing raw evidence. A hypothetical coding agent must reconcile those outputs in code. This small experiment therefore supports raw recovery and explicit binding while rejecting the stronger hypothesis that an answerability/action pair automatically composes into a correct policy.

The plan follow-up is developmental: it was designed after observed failures and is not held-out evidence. Branch outputs unused by the selected operator are ignored, as required by speculative fan-out. The code validates available IDs/edges and simulates a bound plan with in-memory fixture dictionaries; no real file or query engine is exercised. The follow simulation returns the start-source text; it does not implement a full graph traversal or demonstrate end-to-end retrieval. Validation cannot recognize every semantically wrong but structurally legal plan; the wrong lookup above passes its structural validator and remains a failure.

## Concrete next experiments and feature possibilities

1. **Refreshable evidence receipts.** A source revision invalidates derived judgments deterministically, then a narrow survival judgment distinguishes cosmetic changes, scope changes, retractions and historical facts. Save before/after supporting spans and a model/question/source receipt; retain unknown when a deleted source has no replacement.
2. **A bounded semantic query interpreter.** Route into known lookup/compare/follow/select operators. Bind branch-specific arguments speculatively, validate observed IDs/links, and present the exact bound plan and evidence. Require coverage verification for select-all requests so a legal lookup cannot silently satisfy a broader task.
3. **Recoverable context trimming.** Preserve tool protocol and action receipts in code. Judge relevance to current task correctness, with negative constraints and source limitations explicitly in state. Replace hidden text with raw-source handles; compare end-to-end task completion against no trimming, not only compression ratio.
4. **Tiered evidence acquisition with revision metadata.** Summaries should preserve who/when/scope/condition and source revision where applicable. Compare summary-only, source-aware routing, and always-raw policies on cases where the summary sounds complete but is wrong. Measure false confident answers, useful recovery and unnecessary fetches separately.
5. **Explainable source maps.** Extract links and exact source spans locally; Jev can judge relation usefulness, source role, novelty and constraint coverage. Surface unseen/truncated/unverified gaps. A visually complete graph or strong Choice winner must not be presented as complete evidence.

These are research directions. No product implementation, accepted architecture decision, glossary addition or issue change was made.
